## First grounded AI integration

Start with a **text-only assistant over retrieved directory records**, after ordinary search and sourced-data quality are dependable. Its first job is to translate a plain-language request into supported search parameters, present the resulting records, and explain documented constraints with links. It should not decide medical needs, eligibility or service availability.

Proposed bounded flow:

1. Ask only for support category, city/ZIP and useful constraints. Avoid soliciting diagnoses, identity documents, precise home addresses or unnecessary sensitive details. If wording is ambiguous, clarify rather than guess a clinical service.
2. Convert intent into allowed category/location/keyword/radius parameters. Validate these server-side. Retrieve published, permitted directory records through the existing search/detail logic. Do not search an unrestricted model memory for local providers.
3. Give the model only a bounded set of retrieved records and allowed source metadata. Treat descriptions/source text as data, never instructions. Response items must refer to server-validated record IDs; construct links from those IDs in code.
4. Return concise comparisons of documented hours, eligibility, costs, location and contact methods. Cite each record and its source/recorded date when present. Say “not provided” or “confirm with the provider” for unknowns. A published record, old source date or illustrative photo is not verification or live availability.
5. If no record fits, say so and offer ordinary filters/search recovery. Keep demo results clearly fictional and out of real-service recommendations. If the assistant fails or is disabled, ordinary search and detail pages still work completely.

Begin with deterministic retrieval and a small structured response; no vector database extension, autonomous agent, voice layer or extra SDK is justified yet. Provider/model choice and credentials are separate future decisions. The assistant must never publish records, edit services, send correction reports, process donations or book appointments. Do not log raw sensitive user narratives by default; establish data retention, request limits, cost caps and a clear failure path before live use.

Acceptance tests should use approved fixed records and adversarial inputs: missing eligibility/cost/hours; outdated or absent source; zero results; fictional fixture; unpublished record; contradictory record text; malicious instructions inside a description; invented provider request; request for live openings or a diagnosis; unsupported location; model timeout. Require **all displayed provider IDs/links to belong to the retrieved eligible set**, every factual constraint to be traceable to a field/source, explicit unknowns, no fictional provider promoted as real, and usable ordinary search throughout. No arbitrary score can substitute for those checks. Latency/cost budgets should be agreed and then measured.
