## How a search now works

1. The existing local admission checks must pass before EDEN can call a model. Real directory mode additionally requires attested loopback transport, an explicit local opt-in, configured PostgreSQL, no demo rows and a configured Census reference. An ordinary public visitor needs no Gemini session to use Find Support. The separately selected fictional review still accepts only its two known fixture identifiers.
2. For a supported city, the [city lookup](../../backend/directory-city.ts) checks the city's state, unique exact match, Census source/vintage and representative coordinates. Find Support and EDEN use the same center and existing restricted repository. The page requests directory results without optional Places supplements. A radius change retains the city and category.
3. The [directory adapter](../../backend/eden-directory.ts) reads the public results and PostgreSQL total; it verifies source family, imported status, provenance dates, unique IDs, geography and listing order. Up to 20 displayed results can be reconciled; the full count is separate. Opening details rereads the published record. A changed or withdrawn row, unknown source, mixed result set, or mismatched selection cannot become a confirmed model answer. Errors are not reported as successful zero-result searches. Manual controls and external referrals remain available.
4. A typed turn uses the existing Gemini plan → validated action → grounded composition protocol. Live uses the same action checks. The app and its backend may reconcile public service IDs; the model receives controlled page enums, counts, ordinals, approved source labels and dates. It does not receive imported titles, arbitrary source prose, contacts, addresses, coordinates, listing URLs or raw record identifiers through these tools. The typed website can render the actual title after validating the chosen fact ID. Published contacts, source links and dates, eligibility/hours **when supplied**, and the human-operated correction form remain available on the website. EDEN cannot submit a correction, edit an account, make a donation, certify opening status or give medical advice. This limits tool data; separately consented Live microphone audio still reaches Google as audio.
5. Only finite public city metadata is cached: successful lookups for two minutes, concurrent identical lookup requests coalesced. No new cache of listings, addresses, user queries or provider responses. Current result membership/details are queried again before a successful action is confirmed; the page can decline an action if database state changes while it is running.

## The 100/100 resolver limit

At **16:40:34 UTC on Nov 7**, a read-only counter inspection found the legacy resolver daily bucket at **100**, with **26,448 seconds** left. Its window resets at midnight UTC (7 PM Eastern on Nov 7). The limiter admits at most six requests per minute per network and 100 per UTC day in aggregate. Legacy place resolution and a discovery route share that bucket; a demo resolution can use an admission too. The counter has no identity, query or provider-call history. It establishes exhaustion, not which person caused it or that 100 external geocoding or Gemini requests occurred.

The new finite-city route reads only Census data and retains separate reference-route admission. It never forwards the query to an external geocoder. A radius refinement reuses the confirmed center; new directory result sets still come from PostGIS. The legacy resolver respects `Retry-After` in tab memory (deadline only). Redis protection, provider budgets and rejection behavior remain in place. Arbitrary addresses, optional supplements and browser tiles have separate availability/credit limits. A missing city reference returns an actionable failure; retries, wider geographic guesses or a different key are not substitutes. See [Geoapify tile attribution](https://www.geoapify.com/map-tiles/) and [service terms](https://www.geoapify.com/terms-and-conditions/) (retrieved Nov 7, 2026).
