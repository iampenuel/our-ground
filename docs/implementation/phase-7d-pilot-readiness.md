# Phase 7D — Pilot readiness and owner operations

November 5, 2026. **Real-user pilot: NO-GO.** Geoapify is the final selected provider for autocomplete, forward/reverse geocoding and MapLibre map tiles. Earlier Mapbox setup requirements are superseded; no Mapbox credential is required. Nationwide discovery implementation and local checks do not remove the outstanding hosted authentication, database, abuse-control, deployment and operating gates. Production remains unchanged. This document does not authorize deployment, a hosted migration, paid service activation or external account changes.

Read the [Phase 7D implementation report](phase-7d-nationwide-discovery.md), [provider setup](phase-7d-provider-setup.md), [data sources](phase-7d-data-sources.md), and the preceding [Phase 7C security report](phase-7c-security-hardening.md) and [owner guide](phase-7c-owner-readiness.md). Do not reuse Phase 7C totals as evidence that a changed Phase 7D build passed.

## Evidence and release boundaries

Use these classifications separately:

- **IMPLEMENTED AND LOCALLY VERIFIED:** the named code path passed a recorded local test. A synthetic OAuth provider or deterministic location response proves behavior only for that fixture.
- **LIVE PROVIDER VERIFIED:** a recorded real provider request succeeded within the approved request/cost budget. Public food-referral pages were checked, but no telephone call was placed and no food directory API was queried.
- **STAGING VERIFIED:** the exact authorized staged build passed against real nonproduction Auth, PostgreSQL, Redis and map/search services. No new staging deployment is authorized or established by this document.
- **PILOT READY:** all critical gates below pass for a defined population and resource scope. This status has not been reached.

The initial November 5 local inventory inspected names/presence only, never printed credentials. Existing ignored `.env.local` contained Geoapify server/browser key values and Upstash Redis values. Supabase project/client configuration, runtime/owner database connections and a public privacy contact were absent at that inspection. Existing Geoapify keys are available for bounded authorized verification; Mapbox credentials are not required. Geoapify enable/approval flags were not present. Presence of a key is not a successful connection or permission to enlarge its budget. Later owner configuration and real-provider checks must be recorded separately in the main report.

## Exact owner setup and verification sequence

1. Keep Node **24.22.1**, the documented memory-aware environment and the canonical recovered checkout. Preserve the existing uncommitted work. Fill only approved values in ignored local configuration; never put real keys in a report or browser bundle. Follow the [provider setup guide](phase-7d-provider-setup.md) for the actual Phase 7D commands and current token/cost controls.

2. In **Supabase → Authentication → URL Configuration**, set the chosen app origin and exact `/auth/callback` URL. Local verification currently uses `http://127.0.0.1:18418`; a future staged origin must be explicitly selected and authorized. In **Authentication → Providers → Google**, configure the owned Google Web client and its Supabase callback, normally `https://<project-ref>.supabase.co/auth/v1/callback`. This differs from the app callback. In Google Auth Platform, use only identity scopes `openid email profile`, and authorize every testing account used: Organization A, Organization B and the separate reviewer. Never allow `*.vercel.app` or infer a redirect from request input. See [Supabase Google guidance](https://supabase.com/docs/guides/auth/social-sign-in/auth-google).

3. In **Supabase → Authentication → Email / SMTP and Email Templates**, configure an approved sender if email onboarding is in scope. Verify first-time and returning OTP delivery; templates should display `{{ .Token }}` for this code-entry UI. Check expiry, attempts and resend limits at Supabase. Keep email entry disabled until real delivery passes. Default sender restrictions are unsuitable evidence for general recipient delivery. No paid SMTP service is activated by this guide. See [custom SMTP](https://supabase.com/docs/guides/auth/auth-smtp).

4. In database settings, copy the selected direct/session-pooler owner connection for maintenance and a separate `our_ground_api` runtime connection. Confirm TLS enforcement is applied, chain/hostname verification succeeds and an invalid certificate is rejected. Keep private schemas outside Data API exposed schemas; evaluate disabling the unused Data API without disabling Auth. Review **Security Advisor** and relevant exposed schema/function/grant findings. Runtime must own no protected tables/views and have no superuser, role-creation, database-creation or BYPASSRLS rights. Protecting browser/private grants does not make stolen runtime credentials harmless. Use the [Supabase production security checklist](https://supabase.com/docs/guides/security/production-checklist) and reviewed application migration tooling; do not paste arbitrary console SQL into production.

5. Verify real private flows with the three owned accounts. Sign-in alone must grant no listing control. Submit a claim, independently verify organization/location/role using established public contacts, approve/reject with the reviewer, submit a revision and confirm it remains unpublished before approval. Check actor/object/request correlation in safe audits. Organization A must not read or mutate B's private material, and vice versa. Suspend/revoke while keeping the original session token; the next protected request must fail. Verify logout and browser Back show no private content, including mobile/keyboard operation. Do not retain credentials or sign-in codes as evidence.

6. Request separately authorized staging before hosted verification. On that exact candidate, verify public search/giving/maps/details, denied GPS/manual fallback, map-unavailable list behavior, the private account flow, CORS/origin checks, no-store/no-referrer and enforced headers. `Permissions-Policy` must allow same-origin geolocation and deny unrelated camera/microphone/payment features. Public map requests need the approved origin/referrer contract. Resource CSP report-only violations must be reviewed against actual Auth/maps traffic before any stronger enforcement change. No staged or production result can be inferred from local Vite headers.

## Location and provider privacy

The privacy notice now explains typed Geoapify autocomplete/address lookup, optional device coordinates, optional map selection, broad reverse labels, Geoapify mapped discovery/maps, public HRSA provenance and external food referrals. Browser geolocation requires an explicit click and can be declined. Exact GPS/map coordinates use POST search bodies and stay out of share URLs/browser storage; temporary provider locations are not durable organization records. Public city/ZIP context and filters can remain in a URL. The application must not log full address queries or precise resident coordinates, couple anonymous searches to an account, or introduce analytics/session replay. Provider/hosting logs are separate and disclosed.

Geoapify location searches pass through Our Ground, while Geoapify map styles/tiles/fonts connect directly from the browser. Reverse labels use Geoapify when configured. Official food-referral links do not append location parameters, and leave the user to choose what to share at the destination. No account is required for public search. No new medical records, household financial information or file uploads are collected; no HIPAA or other legal-compliance certification is claimed.

## Geoapify key restrictions, attribution and usage

Use **separate** keys: `GEOAPIFY_SERVER_API_KEY` stays server-side for protected location/Places requests, while `VITE_GEOAPIFY_BROWSER_KEY` is intentionally public for map tiles. Both values already exist in the ignored local configuration; their presence alone is not a dashboard-restriction or live-success claim. Actual bounded live evidence is now recorded separately in the implementation report. The same browser key returned 200 from the approved 18418 origin and 401 from the earlier 18428 candidate; no key restriction was changed. New owners obtain a free project key in [Geoapify MyProjects](https://myprojects.geoapify.com/); never paste it into chat or commit it. A shared development key can technically call both paths, but publishing that value exposes server usage to the browser and couples rotation/restrictions. The application uses separated keys, and a shared key must not replace that boundary.

In **MyProjects → selected project → API keys**, inspect each key's **Allowed HTTP referrers**, **Allowed origins** and **Allowed IP addresses**. Restrict the browser key to the exact approved local/production origins; add a temporary staged origin only after staging is explicitly authorized, then remove it after verification. HTTP-referrer/IP fields accept regular expressions, so escape dots and anchor intended origins. Do not allow all Vercel sites. Public discovery's `strict-origin-when-cross-origin` sends the origin rather than a precise search URL; allow that origin-level referrer. Private pages retain `no-referrer` and do not need to send a discovery referrer. Test an approved origin and rejection from an unapproved one without printing key-bearing request URLs. Server keys can use IP restrictions only with confirmed stable egress; do not invent Vercel IPs or weaken browser restrictions to accommodate server requests. The CORS response setting alone is **not** API-key access control. Dashboard changes were not made by this implementation. [Official key restrictions](https://myprojects.geoapify.com/help/api-keys/).

The current free plan has **one shared 3,000-credit daily allowance**, up to **5 requests/second**, and no guaranteed free-plan SLA. Autocomplete, standard forward geocoding and reverse geocoding each cost **1 credit/request**; map tiles cost **0.25 credits/request**. Location search, optional mapped Places discovery and browser tiles consume the same project/account allowance, not separate service allocations. Preserve the application's conservative **200 server-provider requests/day** shared admission; that is a request limit, not a complete project-credit cap. Observe dashboard aggregate credits and request rates, including any other application using the project. Keep the operational warning below the daily ceiling and retain spare allowance; no plan, card or extra credit purchase is authorized. [Free-plan pricing](https://www.geoapify.com/pricing/), [API credit costs](https://www.geoapify.com/pricing-details/).

Estimate geocoding credits as autocomplete calls + forward calls + reverse calls; add 0.25 × actual tile requests and the documented cost of each optional Places request. Report estimates separately from observed dashboard credits. For example, 200 one-credit server calls plus 400 tile requests would be an estimated 300 credits, before other API traffic; that is arithmetic, not measured usage. Browser tile requests bypass server admission, so the backend cannot enforce a full account-level credit ceiling or the combined browser/server request rate. Lazy maps, debounce, short suggestions, zero retries by default (at most one explicitly configured bounded retry) and list fallback reduce use but do not eliminate that limitation.

Keep visible Geoapify/OpenStreetMap/OpenMapTiles attribution and free-plan branding. The existing Geoapify style metadata supplies credits to MapLibre's attribution control; verify they remain visible at desktop/mobile sizes rather than assuming a configured control alone proves compliance. Retain Geoapify attribution beside provider-derived information. The owner must monitor plan usage and review the applicable terms; pricing is not an unlimited-use promise. [Map attribution](https://apidocs.geoapify.com/docs/maps/), [Geoapify terms](https://www.geoapify.com/terms-and-conditions/).

## Privacy operations, retention and incident response

The implemented policy retains correction reports for 90 days; rejected claims/revisions for 180 days; approved-claim contact/explanation fields for 180 days before minimization; security audits for 365 days. Pending unresolved claims do not automatically disappear by age. Minimal access bindings/audit UUIDs and revoked-session denial hashes remain for integrity. The owner-run retention/redaction tooling is separate from public/browser access and defaults to dry-run. Supabase Auth identity deletion is a separate verified owner action.

Follow the exact commands and safeguards in the [Phase 7C owner guide](phase-7c-owner-readiness.md). Verify the request through trusted account channels with a different active administrator. Do not request passwords, OTPs or identity documents. Resolve pending proposals before minimizing data so private text cannot later publish. Do not disable ordinary immutable-audit protections to make retention work. Assign a recurring operator procedure, review its outcomes, and record the last run; this guide installs no production schedule.

For an incident, preserve a minimal restricted timeline and safe request IDs, suspend/revoke affected access and verify actual denial. Rotate an exposed server credential at its provider, update only the approved server environment and prove the old value fails. Keep runtime/owner credentials separate and retain counters when rotating Redis access. Review exposure in history, then rerun source, staged and built-output secret scans. Public publishable keys do not grant administrator authority. Fix the exposure path and reverify before reopening onboarding.

## Acceptable limitations after the blocking gates pass

A defined pilot may disclose that HRSA covers the included health-center program sites rather than every healthcare provider; source publication is not independent organization verification; hours, prices, eligibility and appointment availability may be missing; distances are straight-line, not travel times; and food coverage includes external referral options rather than an imported nationwide pantry directory. These are acceptable only with accurate UI/source labels and a reviewed pilot scope. A provider outage must remain an outage, never an invented empty dataset or fictional substitute.

Feeding America, 211 and the National Hunger Hotline referral evidence is implemented. Food feeds remain unavailable without an actual agreement, permitted-use review and working configured adapter; HSDS is a data format, not a license. These limits do not excuse missing Auth, privacy, abuse protection or hosted-security proof. **Do not open a real-user pilot or begin AI-agent work while the required gates remain unverified.**
