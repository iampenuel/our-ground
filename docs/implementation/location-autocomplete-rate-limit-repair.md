# Location autocomplete rate-limit repair

November 5, 2026 (America/New_York). Machine evidence uses UTC November 6. Local implementation and verification only. No production/staging deployment, environment edit, key/referrer change or AI-agent work.

## Exact root cause

Actual Chrome typing of **new yor** sent one POST to **/api/v1/locations/suggest**. It returned **429 RATE_LIMITED**, with the owner's exact message, “Too many requests. Please wait before trying again.”

Safe captured headers included Retry-After: 73611, Cache-Control: no-store, X-Content-Type-Options: nosniff, Referrer-Policy: no-referrer and request ID 67b2d339-421e-472a-bffd-3130316b51d3. No credential or signed receipt is published.

Read-only Redis TIME/GET/TTL inspection confirmed:

- Public location daily admission: **100/100**.
- Current local location minute admission: **0**, under the 30/minute ceiling.
- Shared server-provider reservations: **116/200**.
- The daily TTL was approximately 20 hours, consistent with the long Retry-After.
- Redis was reachable. This was an intentional application admission denial, not a Redis outage.

The exact text/code is generated by createPublicProtection in backend/anonymous-protection.ts. handleLocationSearch previously applied that provider-oriented daily gate before calling any location adapter or Census lookup. Therefore an exhausted address/provider admission bucket blocked sufficient local Census choices too.

The adapter also always attempted Geoapify autocomplete alongside its reference query, and selecting a signed Census choice attempted implicit Geoapify city-coordinate enrichment. Neither provider operation is necessary to offer or select a clearly labeled representative city point.

The server logs were inspected: they contain the expected local startup line and no unexpected API exception for this handled 429. Request bodies, credentials and precise resident queries are deliberately not logged. Response/code tracing and the read-only counters establish the cause.

## Four distinct limits

| Layer | Meaning and observed state |
| --- | --- |
| Codex verification preload | Internal server-provider test allowance, **12/12**, unchanged. Its exhaustion is a local test error, ordinarily surfaced as unavailable 503, not the observed RATE_LIMITED429. It is not an application/account quota. |
| Our Ground public API admission | Redis-backed application limit. The old shared location daily bucket was100/100 and generated the observed429. All local clients share the local identity; its daily bucket is application-wide. |
| Our Ground shared provider admission | Existing200/day,2/second and12/provider-client/minute protections remain.116 reservations were observed before and after this repair. These are reservations, not proof of provider billing. |
| Geoapify project/account usage | Not inspected. No Geoapify quota-exhaustion claim is made. Browser map usage and other consumers are separate from the server guards. |

Before this change, a lookup could reserve shared provider allowance before the local verification preload rejected dispatch. The local guard itself did not produce the displayed 429, but repeatedly attempting provider work after that guard was exhausted could still add application-counter pressure. Supported local city/state paths now avoid both provider admission and dispatch entirely.

No counters were reset and no ceiling was increased.

## Implementation

1. **Protected reference admission:** location_reference retains 30/minute admission before Census suggestion lookup and Census receipt selection. It has no provider daily charge. Existing location 30/minute+daily admission runs only when provider work is actually needed. The original shared provider limiter still runs before dispatch. Redis failures remain fail-closed before reference work; provider admission failure cannot dispatch a request.
2. **Reference first:** valid exact/fuzzy Census city/state candidates return immediately with providerStatus=not_needed. There is no Geoapify call or provider reservation when these candidates suffice. Returned ambiguity remains visible and requires an explicit choice.
3. **Representative selection:** HMAC/session/expiry-bound Census receipts resolve directly to their recorded representative point. There is no implicit provider enrichment. The existing maximum 64-entry/two-minute public-area cache stores only canonical city/state evidence, never addresses or GPS.
4. **Search-state restoration:** fresh coarse city/state URLs can restore one exact typed Census identity without provider work. New York,NY requires a city; NY is a state. Bare ambiguous New York is not automatically resolved. Cancellation is checked after awaited reference work even if an adapter ignores the signal.
5. **Accurate limits/retry:** safe bounded Retry-After seconds/HTTP-date metadata survives API error handling. A429 button counts down and cannot manually retry early; no automatic request occurs. The live-region message is not repeated every second. Changing the query remains possible. Application/shared429 fallback is labeled limited; quota is reserved for a genuine Geoapify 429 observation.
6. **Duplicate suppression:** the existing 300ms debounce, aborts, stale-response protection, IME behavior and duplicate-retrieval guard remain. Whitespace-only semantic edits now reuse the same query state. Fast typing new yor made one suggestion call before and after the repair; ordinary fast typing was not the primary root cause.

No fuzzy result is auto-selected by popularity. For new yor, actual local data returned New York FL, New York city NY and New York state NY. The browser deliberately selected the NY city identity. Source/type/state labels remain visible.

Street/ZIP paths retain their existing independent checks. City fallback cannot validate a street or house number. No address match or coordinate was fabricated.

## Outcome and remaining limits

**The requested city/state autocomplete cases work again locally, including actual typing and selection.** Refresh the preview to load the new build. The desktop results-left/sticky-map-right layout and clean keyboard focus are preserved.

This is not a claim that every location/provider path is now unrestricted or fully verified. The current Census matcher supports exact and bounded fuzzy names, not every short prefix. Pauses on new, new y or new yo can still enter the admitted provider path when no local candidate exists. Address, ZIP and unsupported-name queries remain subject to the existing application/provider limits and the local verification guard; no fresh live-provider success is claimed for those paths. Clear retry timing and query editing remain available.

Provider-dependent paths remain constrained by the existing exhausted address/test allowances; the repair does not disguise those limits as Geoapify account quota. No comprehensive resource coverage, precise-address guarantee, hosted authentication readiness or pilot readiness is implied.
